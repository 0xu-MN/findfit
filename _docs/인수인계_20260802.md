## 1. 세션 배경

전 세션(`인수인계_20260801.md`)에서 "리뷰어 품질 관리 재검토" Phase 1만 끝난 상태였는데, 이번 세션엔 사업주가 그 이어달리기 대신 완전히 새로운 완성 스펙(리포트 콘텐츠 고도화 8개 항목)을 전달했습니다. 실행 순서는 스펙 원문의 1→8 순서가 아니라 **위험도/작업량이 작은 것부터** 재정렬해서 진행했습니다: `[7]→[6]→[8a]→[8b]→[8c]→[8d]→[3]→[4]→[5]→[2]→[1]`. 매 항목마다 `tsc --noEmit`으로 타입체크했고, 전체 완료 후 `next build`까지 통과 확인했습니다.

**리뷰어 품질관리 Phase 2~6(전 세션 §6-5)은 이번 세션에서 다루지 않았습니다 — 여전히 미착수 상태입니다.**

## 2. [1] Claude 웹검색 도구 연동

- [lib/ai/claude.ts](lib/ai/claude.ts): `callClaude()`에 `options.useWebSearch?: boolean` 추가. 켜지면 Anthropic 서버사이드 웹검색 도구(`web_search_20250305`, `max_uses: 3`)를 요청 body에 추가.
- 응답의 텍스트 블록엔 이제 검색 라운드마다 여러 개의 `text` 블록이 올 수 있어, **마지막** text 블록을 최종 답변으로 사용하도록 변경(`extractSources()`가 `citations`/`web_search_tool_result` 블록에서 출처 URL을 모음).
- 파싱된 JSON이 객체(배열 아님)이면 `_sources`라는 내부 전달용 키를 얹어서 반환 — [lib/ai/generateReport.ts](lib/ai/generateReport.ts)가 이걸 뽑아 `report_data.sources`로 옮기고 `_sources`는 삭제.
- **웹검색은 Standard/Deep 리포트 생성 호출에서만 켜짐** (`projectForReport.project_type !== 'light'`) — Light(무료 전용)나 챗봇/추천 같은 가벼운 호출엔 안 켜짐(비용/지연 때문에 스펙에서 명시적으로 요구한 제약).
- [lib/ai/prompt.ts](lib/ai/prompt.ts) market_size/positioning_map/competitor_references 지시문을 "웹검색 결과를 우선 근거로, 확인 안 되면 추정이라고 명시"로 변경.
- 화면: [components/report/ReportPaidSections.tsx](components/report/ReportPaidSections.tsx) 최하단에 "출처" 각주 블록 추가, [app/builder/reports/[id]/page.tsx](app/builder/reports/[id]/page.tsx)에 배선.

**⚠️ 미검증**: 실제 `ANTHROPIC_API_KEY`가 있는 환경에서 웹검색이 실제로 도는지, 응답 지연이 허용 범위인지 아직 실측 안 함(로컬은 API 키 없이 mock 경로로만 돌렸음 — mock은 `_sources`를 만들지 않으므로 출처 각주가 안 뜨는 게 정상).

## 3. [2] 크리에이터 재무 입력 → 유닛 이코노믹스 실제 계산

- [components/builder/new-request/Step6Pricing.tsx](components/builder/new-request/Step6Pricing.tsx)의 Standard/Deep 비용 확인 단계에 **선택 입력** 3개 추가: 예상 판매가/예상 원가(단위)/월 마케팅 예산.
- [components/builder/new-request/submitProject.ts](components/builder/new-request/submitProject.ts): 셋 다 0(미입력)이면 `extra_data.financials`를 `null`로, 하나라도 입력되면 `{ expectedPrice, expectedCost, marketingBudget }`로 저장.
- [lib/ai/generateReport.ts](lib/ai/generateReport.ts): **AI 호출 없는 순수 계산 함수** 신설.
  - `LTV = (판매가 - 원가) × 예상 구매횟수`, 예상 구매횟수는 `1 + (sean_ellis_pct/100) × 3`(핵심 만족도가 높을수록 반복구매 가능성을 가산하는 단순 추정 — 감사받은 재무모델 아님, 코드 주석에 명시).
  - `CAC = 마케팅예산 ÷ 예상 확보 인원`, 예상 확보 인원은 `reviews.length × (purchase_intent_pct/100)`(최소 1명).
  - **재무 정보 미입력이면 `unit_economics`는 무조건 `null`** — AI가 생성했더라도 `if ('unit_economics' in aiResult) aiResult.unit_economics = unit_economics`로 강제 덮어씀(하드 가드, 스펙이 명시적으로 요구한 부분).
- 화면: `unit_economics`가 null이면 [components/report/ReportPaidSections.tsx](components/report/ReportPaidSections.tsx)에 "재무 정보를 입력하면 계산됩니다" 안내 카드로 대체.

## 4. [3][4][5] 신규 문항 5종

모두 [components/builder/new-request/types.ts](components/builder/new-request/types.ts)에 고정 문항으로 정의하고, [submitProject.ts](components/builder/new-request/submitProject.ts)의 `buildQuestionRows()`에서 자동 삽입되도록 배선했습니다. `Question.type`에 `likert_5`를 새로 추가했습니다(기존엔 wizard 커스텀 문항 타입에 없었고 DB `ReviewQuestionType`에만 있었음).

| 문항 | question_key | 노출 조건 | 용도 |
|---|---|---|---|
| 문제 강도 (1~5) | `psf-severity` | **조건부** — psf-1에서 "자주/가끔 겪는다"로 답한 사람에게만 (`PSF_1_EXPERIENCED_OPTIONS`) | 리뷰 작성 화면([components/evaluator/ProjectCardExpandable.tsx](components/evaluator/ProjectCardExpandable.tsx))에서 psf-1 답변을 보고 숨김 처리 — 필수 답변 체크에서도 같이 제외됨 |
| 기존 대안 | `psf-alternatives` | PSF 단계 전체 | `question_summary`에 자동 집계(객관식이라 기존 로직 그대로 재사용), competitor_references 프롬프트가 이 실데이터를 우선 근거로 쓰도록 지시문 추가 |
| 타겟 적합도 자기평가 (1~5) | `target-fit` | PSF/PMF 공통, 항상 포함 | Sean Ellis 비율을 타겟군 내(4~5점)/밖(1~2점)으로 분리 재집계 → `report_data.sean_ellis_segments` → 프롬프트에 전달해 `pivot_scenarios`가 이 데이터를 근거로 판단하도록 지시 |
| Van Westendorp 가격 4문항 | `vw-too-cheap`/`vw-cheap`/`vw-expensive`/`vw-too-expensive` | PSF/PMF 공통, 항상 포함(단답형 금액 입력) | 중앙값 계산 → `report_data.van_westendorp.acceptable_price_range` (순수 계산, AI 아님) |
| 유입 경로 | `pmf-acquisition-channel` | PMF 단계만(베타/출시) | `question_summary` 자동 집계 + GTM 전략 프롬프트가 실채널 데이터를 우선 근거로 쓰도록 지시 |
| 이탈 위험 기능 | `pmf-churn-feature` | PMF 단계만 | scaleup_roadmap 우선순위를 이 서술형 응답 근거로 정하도록 프롬프트 지시 |

**⚠️ 스펙과 다르게 단순화한 부분** (시간 제약으로 판단한 트레이드오프, 다음 담당자가 필요시 개선):
- **Van Westendorp는 스펙상 "선택"이지만 등록 마법사에 토글 UI가 없어서 항상 포함**시켰습니다. 값 미기입 시 리포트 집계 단계에서 자연히 제외되니 기능적 문제는 없지만, "선택"을 원한다면 Step6에 토글 추가 필요.
- **솔루션 컨셉 A/B/C 비교**(스펙 [3]의 세 번째 항목)는 별도 UI를 만들지 않았습니다 — 기존에 이미 존재하던 "커스텀 객관식 문항"(크리에이터가 옵션 2~6개를 직접 입력) 기능으로 동일한 기능을 이미 충족할 수 있다고 판단해 생략했습니다. 전용 UI(전용 라벨링, ab_test 3개 옵션 지원 등)를 원하면 별도 작업 필요.
- 타겟 적합도 세분화/Van Westendorp 결과는 [components/report/StandardReportView.tsx](components/report/StandardReportView.tsx)에 표시하지만, **PMF 유입경로/이탈위험기능은 question_summary 자동 집계에만 의존**하고 전용 시각화 카드는 안 만들었습니다.

## 7. [8] 기존 확정 항목 재확인/구현

전 세션 §6-5의 Phase 3/4와 겹치는 항목들을 이번 스펙 [8]에서 다시 요청받아 처리:

- **서버측 답변 검증** ([app/api/reviews/[matchId]/submit/route.ts](app/api/reviews/[matchId]/submit/route.ts)): 전 세션 §6-1에서 지적했던 "클라이언트에만 있던 단답/성의없음 검증"을 서버에도 추가. 두 곳이 각자 상수를 갖고 있으면 나중에 어긋날 위험이 있어 [lib/reviewValidation.ts](lib/reviewValidation.ts)(신규)에 `MIN_SHORT_ANSWER_LENGTH`/`CARELESS_ANSWER_PATTERN`을 공용으로 빼서 [components/evaluator/ProjectCardExpandable.tsx](components/evaluator/ProjectCardExpandable.tsx)와 서버 라우트 양쪽이 같은 값을 import.
- **domain_tags 필수 게이트**(전 세션 §6-5 Phase 2): 매칭 수락 시점이 아니라 **리뷰 제출 시점**에 게이트를 걸었습니다(매칭 수락 UI보다 제출 라우트가 훨씬 간단하고 확실한 지점이라 판단). 서버는 403 반환, 클라이언트는 사전 체크 + 에러 메시지에 "지금 바로 직군 선택하러 가기 →" 버튼(기존 휴대폰 인증 게이트와 동일 패턴).
- **ai_reports_history**(전 세션 §6-5 Phase 3): `supabase/migrations/041_ai_reports_history.sql` 신규 — `project_id`/`report_data`/`replaced_at` 등을 담는 백업 전용 테이블(RLS 정책 없음, service role 전용). [lib/ai/generateReport.ts](lib/ai/generateReport.ts)가 upsert 직전에 기존 row가 있으면 이 테이블로 복사.
  - **⚠️ 마이그레이션 041은 아직 실제 DB에 적용 안 됨** — 전 세션의 040처럼 서비스 롤 키로는 DDL을 실행 못 하므로, 사업주가 Supabase 대시보드 SQL 에디터에서 직접 실행해야 합니다. **적용 전까지는 `ai_reports_history` insert가 계속 조용히 실패**할 텐데, 코드가 그 에러를 캐치하지 않고 있어서 — 다음 담당자는 마이그레이션 적용 여부부터 확인할 것.
- **benchmark_comment 실데이터화**(전 세션 §6-5 Phase 4, "확인조차 안 됨" 상태였던 것): 확인 결과 스펙 지적대로 **AI가 실제 비교 수치 없이 자유 생성하는 텍스트**였습니다. `report_benchmark_logs`에서 같은 category+stage로 쌓인 실제 `psf_score` 평균을 계산해서 AI가 생성한 문구를 무조건 덮어쓰도록 수정. 표본 3건 미만이면 "비교 데이터 부족" 문구로 대체(`MIN_BENCHMARK_COMMENT_SAMPLES = 3`, 2단계 승격 기준 `MIN_BENCHMARK_SAMPLE_SIZE = 50`과는 별개의 낮은 임계값 — [lib/ai/constants.ts](lib/ai/constants.ts) 참고).

## 8. 검증 상태 — 다음 담당자가 반드시 확인할 것

스펙 원문의 "검증" 항목 3개 중 **코드/타입 레벨로만 확인했고 실사용 흐름으로는 확인 못 한 것**:

1. **마이그레이션 041 미적용** (위 §7 참고) — 가장 먼저 처리 필요.
2. **웹검색 실제 동작/지연시간** — `ANTHROPIC_API_KEY` 있는 환경에서 실제 리포트 1건 생성해보고 확인 필요.
3. **재무 정보 없이 리포트 생성 시 에러 없음**은 타입/로직 레벨로 확인(널 가드 전부 확인)했으나, 실제 프로젝트로 end-to-end 실행은 안 해봄.
4. **신규 문항 5종의 마법사 노출/숨김**: `psf-severity` 조건부 숨김 로직은 코드 리뷰로 확인했으나, 실제 리뷰 작성 화면에서 psf-1 답변 전/후 눈으로 확인은 안 함.
