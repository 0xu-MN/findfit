## 1. 인증/로그인 — 치명적 버그 3건

전부 실제 서비스 이용을 완전히 막고 있던 버그였고, 전부 코드 문제였다(외부 설정 문제 아님).

### 1-1. 네이버 로그인 — 재로그인 시 항상 "계정 생성 실패" (커밋 `c12bd45`)
`admin.auth.admin.createUser()`가 이미 가입된 이메일에 대해 실제로 던지는 에러 메시지는 `"A user with this email address has already been registered"`인데, 코드는 `.includes('already registered')`로 판별하고 있었다. `"already"`와 `"registered"` 사이에 `"been"`이 껴 있어서 이 substring 매칭은 **한 번도 성공한 적이 없다** — 즉 이미 가입한(=거의 모든 재로그인) 네이버 사용자가 매번 진짜 에러로 오인돼 로그인이 막혔다.

수정: [app/api/auth/naver/callback/route.ts](app/api/auth/naver/callback/route.ts) — 문자열 대신 `createErr.code !== 'email_exists'`로 판별.

### 1-2. 네이버 로그인 — public.users row 누락으로 휴대폰 인증 전멸 (커밋 `5c88854`)
`admin.auth.admin.createUser()`로 만든 계정은 `auth.users`에는 생기지만, `handle_new_user` 트리거가 안정적으로 안 타서 `public.users` row가 아예 안 만들어지는 경우가 실제로 확인됐다(DB 직접 조회로 증명 — `auth.users`엔 있는데 `public.users`엔 없는 실제 계정 발견). 이 상태에서 휴대폰 인증코드를 저장하려 하면 `phone_verifications.user_id` 외래키 위반으로 매번 500 "인증코드 발급에 실패했습니다"가 났다.

수정: 콜백에서 `verifyOtp` 성공 직후 `public.users`를 직접 upsert해서 없으면 만들어 방어. 이미 막혀있던 실제 계정(`hongsumin0608@naver.com`)도 그 자리에서 직접 백필함.

**다음 담당자 참고**: `handle_new_user` 트리거([supabase/migrations/015_fix_handle_new_user_search_path.sql](supabase/migrations/015_fix_handle_new_user_search_path.sql))가 admin API 경로에서 왜 간헐적으로 안 타는지 근본 원인은 아직 안 밝혀졌다 — 지금은 콜백에서 방어적으로 upsert하는 걸로 막아뒀지만, 다른 admin API 호출 경로(예: 구글/카카오 소셜 로그인은 Supabase 표준 OAuth라 이 문제가 없을 가능성이 높음)에서도 같은 증상이 재발할 수 있으니 유저 관련 버그 리포트가 오면 이 패턴을 의심할 것.

### 1-3. 일반 회원가입 — 중복 이메일 시 영문 원본 에러 노출 (커밋 `c12bd45`)
`check-availability`가 `public.users`만 확인해서, `auth.users`에는 있지만 `public.users`엔 없는 이메일(가입 중간에 끊긴 경우 등)은 "사용 가능"으로 잘못 통과된 뒤 실제 `signUp()` 시점에 `"User already registered"` 영문 원본 에러가 그대로 노출됐다. [app/auth/signup/page.tsx](app/auth/signup/page.tsx)에서 `error.code === 'user_already_exists'`를 명확한 한글 메시지로 매핑하도록 수정.

## 2. 모집·리뷰·리포트 파이프라인 버그

### 2-1. 조기 마감 프로젝트 리포트 영구 미생성 (커밋 `73d98a2`) — **가장 중요**
크리에이터가 목표 인원 미달로 모집을 조기 종료(`force_early`/`proceed_short`)하면, [close-recruitment/route.ts](app/api/projects/[id]/close-recruitment/route.ts)가 `projects.target_count`를 원래 값 그대로 뒀다. 그런데 리뷰 제출 완료 체크([app/api/reviews/[matchId]/submit/route.ts](app/api/reviews/[matchId]/submit/route.ts))는 `completed_count >= target_count`로 리포트 자동생성 여부를 판단하므로, 실제 수락 인원 전원이 리뷰를 완료해도 `completed_count`가 원래 `target_count`에 절대 도달하지 못해 **리포트가 영원히 생성되지 않는다**. 실제로 "6명 모집·5명 수락·5명 전원 리뷰 완료"인 프로젝트가 이 상태로 멈춰있는 걸 발견하고 DB에서 직접 복구했다.

수정: 조기 마감 시 실제 수락 인원(`project_matches` 중 `accepted`/`completed` 카운트)으로 `target_count`를 맞춰 내려주도록 수정.

**다음 담당자 참고**: 이 버그의 파급력이 커서, 과거에 조기 마감된 다른 프로젝트 중에도 같은 문제로 멈춰있는 게 있을 수 있다. 아래 쿼리로 점검 권장:
```sql
select id, title, status, target_count, completed_count
from projects
where status = 'reviewing'
  and completed_count < target_count;
-- 이 중 project_matches의 accepted+completed 합이 completed_count와 같은데
-- target_count보다 작은 것들이 "조기마감했는데 target_count가 원래 값으로 남은" 후보.
```

### 2-2. AI 리포트 생성 500 에러 — Claude 확장 사고(thinking) 블록 (커밋 `36cf2ff`)
`lib/ai/claude.ts`의 `callClaude()`가 `data.content[0]`을 무조건 text 블록으로 가정했는데, sonnet이 리포트 생성처럼 긴 구조화 출력에서 `thinking` 블록을 먼저 반환하는 경우가 실제로 있었다(`content: ['thinking', 'text']`). 이 경우 `text`가 빈 문자열이 되고 `JSON.parse('')`가 "Unexpected end of JSON input"만 던져서 원인 파악이 어려웠다. `content` 배열에서 실제 `type === 'text'`인 블록을 찾도록 수정 + `max_tokens`도 2000→8000으로 올림(구조화 필드가 많아 잘릴 위험 방지) + 진단용 에러 메시지에 `stop_reason` 포함.

### 2-3. 모집 정원 판단 로직 — `completed_count` vs 실제 수락 인원 (커밋 `106d4c1`)
`completed_count`는 "리뷰 제출 완료 수"라서 모집 중(`active`)엔 항상 0인데, 여러 곳에서 이 값으로 "모집 마감 여부"를 판단하고 있어서 실제로는 자리가 다 찼는데도 지원이 계속 들어오는 버그였다. `project_matches`에서 `pending`/`accepted`/`completed` 상태 카운트(`occupied_count`)로 판단하도록 수정 — `apply`/`join` API, `feed` API, `ProjectCardExpandable.tsx`, `ProjectDetailPage.tsx` 전반.

### 2-4. PSF 고정 문항이 프로젝트 맥락 없이 "이 문제", "이런 솔루션"만 물어봄 (커밋 `052fe32`)
Standard 리뷰의 고정 문항("이 문제를 직접 겪어보신 적이 있나요?", "이런 솔루션이 있다면 사용해보시겠어요?")이 지시어만 있고 실제 프로젝트의 문제/솔루션 내용을 안 보여줘서 리뷰어가 맥락 없이 답해야 했다. [components/evaluator/ProjectCardExpandable.tsx](components/evaluator/ProjectCardExpandable.tsx)의 `ReviewFormPanel`에 `problem`/`solution` prop을 추가로 넘겨서, `question_key`가 `psf-1`/`psf-2`/`psf-3`인 문항 위에 실제 내용을 표시.

### 2-5. 기타
- 관리자 반려 처리가 리뷰어 화면에 전혀 반영 안 되던 문제(`106d4c1`) — "내 리뷰" 목록/프로젝트 상세에 반려/취소 상태 표시 추가.
- `question_type: 'keyword'`가 `allow_multiple` 상관없이 항상 다중 선택으로 동작해서, 단일 선택이어야 하는 질문에도 여러 답이 한꺼번에 저장되던 버그(`36cf2ff`).
- AI 제안 선지("AI 제안 선지로 채우기")를 받은 뒤 "+ 선택지 추가"로 슬롯을 늘리면 새 슬롯엔 제안이 없던 문제(`052fe32` 근처) — 슬롯 추가 시 늘어난 개수로 재요청하도록 수정.

## 3. FindFit Agent 개선

### 3-1. 등록 마법사 프로젝트 내용을 Agent가 못 읽는 문제 — 진짜 원인은 stale closure (커밋 `cc0530f`)
등록 마법사에서 바로 등록(아이템 탐색 경유 안 함) 진입 시, Agent에게 "지금 등록 중인 프로젝트 내용을 보고 뭘 검증해야 하냐"고 물어봐도 계속 "아직 아이디어를 말 안 해줘서 모른다"고 답하는 버그. 마법사가 현재 단계/입력 내용을 `AgentBubbleContext`에 실시간으로 넘기는 코드 자체는 있었는데, `AgentPanel.tsx`의 `processInput` 콜백(`useCallback`)의 의존성 배열에 `agentBubble.activeWizardStep`이 빠져 있어서, 다른 이유로 메모이즈된 콜백이 재사용될 때 예전 값(널 포함)을 계속 참조하는 stale closure였다. 의존성에 추가해서 해결 — API에 직접 페이로드를 보내 실제로 Claude가 프로젝트 내용을 인지하고 답하는 것까지 확인했다.

### 3-2. 등록 마법사 컨텍스트가 "지금 단계" 필드만(그마저 6단계 중 4단계만) 넘어감 (커밋 `6dea7f7`)
[components/builder/NewRequestPage.tsx](components/builder/NewRequestPage.tsx)의 `fieldsHint` 계산이 `questions`/`attachments` 단계는 아예 처리 안 돼 있었고, 그마저도 "지금 단계" 필드만 넘겨서 이전 단계에 입력한 제품명/문제/타겟 등을 Agent가 몰랐다. 지금까지 입력된 프로젝트 전체(제품명/한줄소개/분야/단계/타입/문제/대안/차별점/타겟/검증목표/가설)를 항상 요약해서 넘기도록 수정.

### 3-3. Agent 대화가 새로고침하면 사라지고, 새 아이템 탐색 시 이전 대화와 섞임 (커밋 `106d4c1`)
`FloatingAgentBubble`이 세션 내내 마운트 유지되는 설계라 새로고침하면 메모리상 대화가 통째로 날아갔고, 반대로 새 아이템 탐색을 시작해도 이전 대화 위에 새 seed가 이어붙기만 했다. `localStorage`(`findfit_agent_active_conversation`)로 일반 대화를 지속 저장하고, 진짜 새 seed가 오면 리셋하도록 수정. 프로젝트 등록 완료/리포트 모드 진입 시엔 정리.

### 3-4. Agent 대화 → 리포트 모드 이어가기 (커밋 `106d4c1`)
프로젝트 등록 시 CTA 클릭 시점의 대화 전문을 `agent_conversation_logs` 테이블(마이그레이션 036)에 저장해두고, 나중에 그 프로젝트의 리포트 모드로 들어가면 저장된 대화를 이어서 보여주도록 구현. (이 테이블에 실제 대화 원문을 저장하는 건 예전 "경량 이관(요약만 보관)" 결정을 이 기능 한정으로 확장한 것 — 마이그레이션 파일 주석 참고.)

### 3-5. Agent 추천 질문이 매번 똑같음 (커밋 `106d4c1`)
`buildSuggestedQuestions`가 컨텍스트(트렌드 유무/타겟 유무)만 보고 고정된 4개를 반환해서 사실상 항상 같은 문구였다. 카테고리별 문구 풀(pool)을 만들고, `context.shownSuggestions`에 이미 보여준 걸 기록해서 다음엔 다른 문구를 고르도록 수정.

### 3-6. Phase 2 타겟 확인이 자유 텍스트로는 진행이 안 되던 문제 (커밋 `106d4c1`)
Claude가 자유 텍스트에서 `target_customer`를 확신 있게 못 뽑아내면 "아직 모르겠어요" 토스트 버튼을 눌러야만 다음 단계로 진행됐다. `applyUnderstanding`에 사용자의 발화 자체를 타겟으로 채택하는 폴백을 추가.

## 4. 관리자 패널 전면 개편

### 4-1. 대시보드 신설 (커밋 `cc0530f`)
`app/admin/page.tsx`를 실제 KPI(신규지원/정산대기/검수대기/진행중/전체 유저/결제 전환율/누적 결제액) + 일별 신규가입 막대그래프 + 분야별 프로젝트 분포 도넛 차트(CSS `conic-gradient`, 별도 차트 라이브러리 없음)로 재구성.

### 4-2. 전체 페이지 다크 테마 통일 (커밋 `08d36ec`)
대시보드만 새 디자인이고 나머지 서브페이지(지원자/정산/검수/유저/인사이트/배너/통계 관리)는 옛날 흰 배경 그대로였던 불일치를 해결. `components/admin/AdminSidebar.tsx`를 공용 컴포넌트로 분리하고 `app/admin/layout.tsx`에서 로그인 페이지를 제외한 모든 `/admin/*`에 공통 적용.

### 4-3. 라이트/다크 토글 (커밋 `73d98a2`)
"다크만 있으니 눈 아프다" 피드백으로 추가. [app/admin/admin-theme.css](app/admin/admin-theme.css)에 시맨틱 클래스(`admin-page`/`admin-card`/`admin-text`/`admin-text-dim`/`admin-border` 등)를 CSS 변수로 정의하고, 기존 하드코딩된 Tailwind 임의값(`bg-[#15171C]`, `text-white/40` 등)을 전부 이 클래스로 교체. `data-admin-theme` 속성을 `localStorage`(`findfit_admin_theme`)에 저장해 토글.

**주의**: 배지/버튼처럼 **솔리드 색상 배경 위의 흰 텍스트**(`bg-[#1565C0] text-white` 같은 패턴)는 의도적으로 그대로 뒀다 — 테마 무관하게 항상 흰 글씨여야 하는 경우라 시맨틱 클래스로 바꾸면 안 됨. 앞으로 관리자 페이지에 새 UI를 추가할 때 이 구분을 유지할 것(페이지/카드 배경 위 텍스트 → `admin-text*` 클래스, 채도 있는 solid 배경 위 텍스트 → 그대로 `text-white`).

### 4-4. 실시간 활동/참여 세부현황 (커밋 `73d98a2`)
세션 로그 테이블이 없어서 완벽한 실시간 측정은 불가능 — 대신 실제 행동(프로젝트 등록/지원/제출) 타임스탬프를 5분/오늘/7일 3단 창으로 나눠 근사. [app/admin/stats/page.tsx](app/admin/stats/page.tsx)에 진행 중 프로젝트별 참여 세부현황(대기/수락(미제출)/완료/이탈 인원) 테이블도 추가 — "신청해놓고 참여 안 하는 사람"을 여기서 확인 가능.

### 4-5. 관리자 계정 보호 (커밋 `6dea7f7`)
`app/admin/evaluators/page.tsx`의 관리자 계정 보호 로직이 `u.role !== 'admin'`으로 돼 있었는데, `role` 컬럼은 가입 시 고정되는 `'builder'`/`'evaluator'`뿐이라 **`role === 'admin'`인 유저가 DB에 존재한 적이 없다** — 즉 이 가드는 사실상 죽은 코드였고, 실제 관리자 계정(`haloforge@haloforge.kr`, `is_admin: true`)도 정지/탈퇴 버튼이 그대로 눌리는 상태였다. `is_admin` 컬럼 기준으로 프론트에서 버튼 자체를 안 보여주고, [app/api/admin/users/[id]/status/route.ts](app/api/admin/users/[id]/status/route.ts) 서버에서도 이중으로 막도록 수정.

## 9. 로컬 개발 시 주의사항

- **로컬과 Vercel(findfit.vercel.app)이 같은 Supabase 프로젝트(같은 DB)를 공유한다.** 로컬에서 테스트 계정을 만들면 실제 운영 DB에 남는다 — 테스트 후 정리 습관화.
- **푸시 전 반드시 `npx next build`를 실행해서 실제로 빌드가 통과하는지 확인할 것.** `npx tsc --noEmit`만으로는 안 잡히는 빌드 전용 에러(예: `useSearchParams` Suspense 요구사항)가 있다 — 섹션 6 참고, 이걸로 실제 배포 사고가 났었다.
- **Agent 위젯은 세션 내내 마운트 유지**되는 의도된 설계다(`FloatingAgentBubble.tsx`) — 대화 상태가 페이지 이동에도 안 끊기게 하려는 것. 대신 이번 세션에서 `localStorage` 지속성도 추가했으니, 새로고침해도 일반 대화는 유지된다(리포트 모드 진입/등록 완료 시엔 정리됨).
- **휴대폰 인증**: `SOLAPI_API_KEY`가 없으면(현재 상태) 실제 SMS는 안 나가고, `/api/auth/phone/send` 응답에 `devCode` 필드로 코드가 함께 내려와 화면에 표시된다 — 로컬/Vercel 둘 다. 여러 테스트 계정을 인증하려면 `users.phone`에 UNIQUE 제약이 있으니 **계정마다 다른 번호**를 써야 한다(같은 번호 재사용 시 두 번째 계정부터 "이미 가입된 번호" 에러).
- **관리자 패널 접근**: `/admin/login`에서 `is_admin=true` 계정으로 일반 로그인, 또는 관리자 전용 임시 비밀번호 경로(이전 인수인계 문서 참고). 관리자 페이지는 전부 `app/admin/layout.tsx`가 공통 사이드바+테마를 씌우므로, 새 관리자 페이지를 추가할 때는 `admin-theme.css`의 시맨틱 클래스를 쓸 것(섹션 4-3 참고).
- **`npx tsc --noEmit`과 `npx next build` 둘 다 이번 세션 마지막 커밋 기준으로 클린 통과 확인됨.**
