## 3. AI 추천/Agent mock 응답 개선

**배경**: `.env.local`(로컬)과 Vercel 환경변수 양쪽 다 `ANTHROPIC_API_KEY` 관련 이슈가 있었음 — 처음엔 아예 없어서 mock 폴백만 타고 있었고(1차), 사용자가 Vercel에 키를 넣은 뒤에도(3차 후반) 여전히 문제가 있어서 직접 Vercel 배포 URL에 curl로 여러 번 호출해서 원인을 찾아냄(6장 참고).

### 3.1 mock 응답을 phase/키워드에 반응하게 개선 (`lib/ai/claude.ts`)
- **Agent 이해 프롬프트**(`prompt.includes('창업 아이디어 상담 에이전트')` 분기): 이전엔 phase와 무관하게 고정 인사말 하나만 반환 → 프롬프트 안의 phase 마커 텍스트(`buildAgentUnderstandingPrompt`의 `phaseInstruction`)로 지금 몇 단계인지 판별해서, phase 2(타겟 파악)에서는 사용자가 입력한 텍스트를 그대로 `target_customer`로 채워 반환, phase 3+에서는 `ready_for_cta: true` 반환. `agentMock.ts`의 `applyUnderstanding`이 그대로 이 필드를 읽어서 phase를 진행시킨다(로직 변경 없음, mock 응답만 개선).
- **아이템 추천 프롬프트**(`prompt.includes('창업 아이템 추천 에이전트')` 분기): 이전엔 입력 키워드와 무관하게 완전 고정된 3개("저당 간식 정기구독 키트" 등)만 반환 → 프롬프트에서 `[사용자 입력 키워드]`를 정규식으로 추출해서 `${keyword} 정기구독 키트` 같은 템플릿에 반영.

### 3.2 recommend-items 라우트 자체의 진짜 버그 수정 (`app/api/agent/recommend-items/route.ts`)
Vercel에 실제 키를 넣은 뒤 직접 curl로 테스트해서 발견한 것 — **mock이 아니라 실제 Claude 호출 경로의 버그**:
- **키워드 무시 버그**: `getTrendLine('default')`을 항상 고정 카테고리로 호출하고 있어서, 참고 트렌드가 항상 "스타트업 서비스 검색량 60% 감소" 한 줄로 고정 → Claude가 실제 입력 키워드보다 이 트렌드 문구를 더 따라가서 "반려동물 간식"을 입력해도 "스타트업 컨설팅" 같은 완전 무관한 추천이 나왔음. `guessCategory(keyword)` 함수(간단한 한글 키워드 매칭)를 추가해서 카테고리를 추정한 뒤 `getTrendLine`에 넘기고, 프롬프트에도 "키워드가 우선, 트렌드는 참고만" 명시.
- **절반 정도 실패해서 폴백되는 문제**: Claude 호출이 가끔 실패(타임아웃/일시적 오류)하면 바로 `FALLBACK_ITEMS`(하드코딩 3개)로 떨어지고 있었음 → 1회 재시도 로직 추가(`for (let attempt = 0; attempt < 2; attempt++)`).

## 4. 🔴 매칭·리뷰 플로우 전면 개편 (가장 중요, 파이프라인 변경 포함)

### 4.1 배경 — 사용자가 명확히 한 요구사항
1. 개별 리뷰어 지원 수락/거절은 **관리자**가 처리(크리에이터가 개별 승인/거절하는 게 아님).
2. 크리에이터에게는 그 대신 **프로젝트 단위 진행 여부 선택권**을 준다 — 상황별로 3가지:
   - **모집 마감일 전 + 목표 인원 미달**: "조기 시작" — 가장 위험(손실 확정), 재확인 모달 필요
   - **모집 마감일 지남 + 목표 인원 미달**: "지금 인원으로 시작"(부족분 환불) 또는 "모집 기간 연장" 중립 선택
   - **목표 인원 달성**: 경고 없이 바로 시작
3. **관리자가 개별 지원을 수락해도, 크리에이터가 프로젝트 단위로 명시적으로 "시작"하기 전까지는 실제로 리뷰가 진행되면 안 된다.**
4. 모집 중인 프로젝트를 실수/고의로 삭제할 때 환불 불가 경고.

### 4.2 개별 승인/거절 → 관리자 전용 (조사 결과 이미 있었음)
조사해보니 `app/admin/applications/page.tsx` + `app/api/admin/applications/[id]/accept|reject/route.ts`가 **이미 다른 세션에서 완전히 구현돼 있었음**(관리자 대시보드의 "지원자 관리" 카드). 그래서 새로 안 만들고:
- `components/builder/ProjectDetailPage.tsx`에서 크리에이터용 개별 수락/거절 UI(`respondToApplicant` 함수 + 수락/거절 버튼, `Check`/`X` 아이콘 버튼)를 **제거**하고, 지원 현황은 "지원 검토 중 (N명) — 관리자가 승인/거절을 처리합니다"라는 읽기 전용 배지로 교체.
- `app/api/builder/matches/[matchId]/accept|reject/route.ts`(크리에이터 전용이던 예전 라우트)는 **삭제하지 않고 그대로 둠** — 호출하는 UI가 없어져서 자연히 죽은 코드가 됐지만, 안전하게 남겨둠(다음 정리 세션 후보).

### 4.3 프로젝트 단위 3가지 시나리오 (신규, `components/builder/ProjectDetailPage.tsx`)
`project.deadline`(이번에 새로 select에 추가함)과 `completed_count`/`target_count`를 비교해서 즉석에서 분기:

```ts
const deadlinePassed = project.deadline ? new Date(project.deadline) < new Date() : false
const targetMet = completedCount >= targetCount && targetCount > 0
```

- **케이스 3(목표 달성)**: 경고 없는 오렌지 버튼 "지금 바로 시작하기" → `close-recruitment` API를 `mode: 'complete_start'`로 호출.
- **케이스 2(마감일 지남 + 미달)**: 중립색 버튼 2개, **모달 없이 즉시 실행**(사용자가 "되돌릴 수 없는 손해가 없는 선택"이라고 명시함):
  - "지금 모인 인원으로 시작하기"(하단에 "부족한 인원만큼의 금액은 전액 환불돼요" 설명) → `mode: 'proceed_short'`
  - "모집 기간 연장하기"(하단에 "며칠 더 기다리며..." 설명) → 신규 `app/api/projects/[id]/extend-deadline/route.ts` 호출(마감일을 현재 시각 기준 +3일로 연장, `status`는 그대로 `active` 유지)
- **케이스 1(마감일 전 + 미달, 가장 위험)**: "모집 마감 전에 조기 시작하기" 버튼 → **재확인 모달**(취소 가능) — "아직 모집 마감일도 안 됐고, 목표한 인원도 다 채우지 못했어요. 지금 시작하면 부족한 인원만큼의 금액을 포함해 이미 결제한 금액은 환불되지 않아요." + 확인 버튼(빨간색, `mode: 'force_early'`)/취소 버튼("마감일까지 기다릴게요").

세 모드 다 `app/api/projects/[id]/close-recruitment/route.ts`가 처리하고, 실제로 하는 일은 동일(`projects.status: 'active' → 'reviewing'`). `mode`는 화면 문구/향후 통계 구분용으로만 응답에 반영(`refundNeeded`, `shortfallCount` 필드로 부족 인원 수와 환불 필요 여부를 계산해서 내려줌).

**⚠️ 환불은 실제로 처리되지 않습니다.** "부족한 인원만큼 전액 환불돼요"는 화면 문구로는 정확히 넣었지만, PortOne 환불 연동이 아직 스텁 상태(`lib/payment/portone.ts`의 환불 함수가 그냥 throw함, 1차 인수인계 문서에서도 확인된 사실)라 실제로 돈이 안 돌아갑니다. `close-recruitment` API가 `refundNeeded`/`shortfallCount`를 응답에 남겨두긴 했지만, **이 값을 실제로 소비해서 환불을 실행하는 코드는 없습니다.** 나중에 결제 연동이 붙을 때 반드시 이 부분을 마저 구현해야 합니다.

### 4.4 🔴 리뷰 제출 파이프라인에 게이트 추가 (`app/api/reviews/[matchId]/submit/route.ts`)
**가장 중요한 변경사항입니다.** 조사해보니 지금까지 이 파이프라인에 project 상태를 확인하는 로직이 **전혀 없었습니다** — 관리자가 개별 지원을 수락하면(`project_matches.status = 'accepted'`) 그 즉시 리뷰어가 리뷰를 제출할 수 있었고, 크리에이터가 4.3의 3가지 선택 중 뭘 하든 안 하든 전혀 상관이 없었습니다.

추가한 게이트(match 소유권 확인 직후, `review_questions` 조회 전):
```ts
const { data: projectGate } = await supabase
  .from('projects_public')  // ⚠️ projects 원본 테이블이 아니라 반드시 이 뷰를 써야 함(아래 참고)
  .select('status')
  .eq('id', projectId)
  .single()
if (projectGate?.status !== 'reviewing') {
  return NextResponse.json(
    { error: '아직 크리에이터가 리뷰를 시작하지 않았어요. 시작되면 알림으로 알려드릴게요.' },
    { status: 403 }
  )
}
```
**`projects` 원본 테이블이 아니라 `projects_public` 뷰를 써야 하는 이유**: `projects` 테이블은 RLS 정책(`projects_owner_all`, migration 009)상 **크리에이터 본인만** SELECT 가능합니다. 리뷰어 세션 클라이언트로 `projects`를 직접 조회하면 RLS에 막혀서 항상 null이 나옵니다. 리뷰어가 봐도 되는 프로젝트 정보는 `projects_public` 뷰(creator_id 제외, migration 009)로만 노출됩니다 — 이번에 `app/api/evaluator/my-reviews/route.ts`(4.5 참고)에서도 똑같은 RLS 함정에 걸려서 원인을 찾은 뒤 다른 파일에도 같은 패턴이 있다는 걸 알아채고 여기도 고쳤습니다.

이 변경 외에 `submit/route.ts`의 나머지 로직(답변 저장, `increment_completed_count` RPC, 리포트 생성 트리거)은 **한 글자도 안 건드렸습니다** — 커밋 diff로 직접 확인 가능(`git show 64c738d -- "app/api/reviews/[matchId]/submit/route.ts"`).

프론트엔드 쪽에서 이 게이트를 미리 알고 폼 자체를 숨기는 처리는 **아직 안 돼 있습니다** — `components/evaluator/ProjectCardExpandable.tsx`의 `ReviewFormPanel`은 리뷰어가 폼을 다 채우고 제출을 눌러야 위 에러 메시지를 받습니다(제출 실패 시 에러는 화면에 정상적으로 뜸, `setError(body.error ?? ...)`). UX 개선 여지가 있음 — 7장 "다음 작업 후보" 참고.

### 4.5 리뷰어 "내 리뷰" — 프로젝트가 "삭제된 것"처럼 보이던 RLS 버그 (`app/api/evaluator/my-reviews/route.ts`)
2차/3차 초반에 만든 "내 리뷰" 페이지에서, 조기 마감된 프로젝트가 "(삭제된 프로젝트)"로 표시되는 버그가 있었습니다. 원인은 4.4와 동일 — `project_matches`에 `projects(...)`를 그대로 Supabase 임베드 조인했는데, RLS 때문에 리뷰어 입장에선 null이 되어버림. `projects` 조인을 제거하고, `project_id` 목록을 모은 뒤 `projects_public` 뷰에서 별도로 조회해서 클라이언트 쪽에서 merge하도록 수정.

### 4.6 프로젝트 삭제 — 환불 불가 경고 모달 (`components/builder/ProjectDetailPage.tsx`)
- `project.status === 'active' || 'reviewing'`(모집 중 또는 리뷰 진행 중)인 프로젝트를 삭제하려 하면, 브라우저 기본 `confirm()` 대신 앱 스타일 모달이 뜸 — "이미 모집된 리뷰어 사례금은 삭제해도 환불되지 않아요" 문구 포함, 취소/삭제 버튼.
- `draft`/`pending_review`(아직 아무도 모집 안 된 상태)는 기존처럼 가벼운 네이티브 `confirm()` 유지 — 굳이 무거운 모달 안 씀.
- `components/builder/ProjectListPage.tsx`(목록 화면, 카드형 삭제 버튼들)는 **이번에 안 건드림** — `ProjectDetailPage.tsx`(상세 화면)만 수정. 목록에서 바로 삭제하는 경로는 여전히 네이티브 confirm 그대로라, 다음 개발자가 필요하면 같은 패턴으로 확장할 것.

## 6. 실제 배포(Vercel) 진단 기록 — 참고할 것

사용자가 `.env.local`에 키를 넣었는데도 안 된다고 해서, `.env.local`은 **로컬 dev 서버 전용**이고 Vercel은 별도 환경변수 저장소를 쓴다는 걸 설명함. 확인해보니 사용자는 실제로 Vercel 대시보드에 키를 넣었었고, 로컬 `.env.local`엔 여전히 없는 상태(`grep -c ANTHROPIC_API_KEY .env.local` → 0).

`https://findfit.vercel.app`에 직접 curl로 여러 번 POST 요청을 보내서(재현/디버깅 목적) 확인한 결과:
- 키 자체는 **작동하고 있었음**(mock 고정 문구가 아니라 실제 생성형 응답이 옴).
- 다만 3.2에서 설명한 두 가지 진짜 버그(키워드 무시, 절반 실패) 때문에 사용자 입장에선 "제대로 안 된다"고 느꼈던 것.

**Vercel 재배포 관련 팁(다음 개발자도 참고)**: Vercel은 환경변수를 추가/변경해도 이미 떠 있는 배포에는 자동 반영되지 않습니다 — Deployments 탭에서 최신 배포를 Redeploy 해야 합니다. 또한 환경변수 등록 시 Production/Preview/Development 범위를 반드시 확인해야 합니다(Production 미체크 시 실제 서비스 도메인엔 반영 안 됨).

## 7. 알려진 이슈 / 다음 작업 후보

1. **환불 미구현** (4.3 참고) — `close-recruitment` API가 `refundNeeded`/`shortfallCount`를 계산은 하지만 실제로 소비하는 곳이 없음. PortOne 환불 연동 붙을 때 최우선으로 마저 구현할 것.
2. **리뷰 제출 게이트의 프론트엔드 UX** (4.4 참고) — 지금은 API 레벨에서만 막고 있어서, 리뷰어가 폼을 다 채우고 제출 버튼을 눌러야 "아직 시작 안 됨" 에러를 봄. `ReviewFormPanel`이 열리기 전에 프로젝트 status를 먼저 확인해서 폼 대신 "아직 리뷰가 시작되지 않았어요" 안내를 보여주는 게 더 나은 UX — `CardProject` 타입에 `status` 필드 추가 필요(현재 없음), 그리고 이 타입을 쓰는 3곳(`app/evaluator/dashboard/page.tsx`, `app/evaluator/projects/page.tsx`, `app/evaluator/projects/[id]/page.tsx`)의 select 쿼리에도 `status` 추가해야 함.
3. **자동 마감 크론(`supabase/functions/expire-deadlines`)과의 상호작용 미검증** — deadline이 지나면 매일 자정 cron이 `active` 상태 프로젝트를 자동으로 `completed`로 바꿔버리는 기존 로직이 있음(4.3의 케이스 2 UI가 뜨기도 전에, 크리에이터가 하루 넘게 방치하면 cron이 먼저 처리해버릴 수 있음). 실제로 두 로직이 충돌하는 경우를 시나리오 테스트해보지 않았음 — 다음 개발자가 확인 필요.
4. **`ProjectListPage.tsx`의 삭제 버튼들**은 여전히 네이티브 `confirm()`(4.6 참고) — `ProjectDetailPage.tsx`와 다른 경험. 통일하려면 같은 모달 패턴을 그쪽에도 적용할 것.
5. **`app/api/builder/matches/[matchId]/accept|reject/route.ts`**는 죽은 코드로 남아있음(4.2 참고) — 삭제해도 되는지 다음 세션에서 재확인 후 정리.
6. 1차/2차 인수인계 문서에 있던 기존 이슈들(라운지 백엔드 미연동, 인사이트 좋아요/저장 미영속, PortOne/SOLAPI 실키 미연동 등)은 이번 구간에서도 그대로입니다.
7. **`components/landing/HowItWorksSection.tsx`**가 계속 커밋 안 된 상태(`git status`에 수정됨으로 표시)로 여러 세션째 남아있습니다. 원인 불명이라 계속 커밋 안 하고 넘어가는 중 — 다음 개발자가 `git diff`로 확인 후 처리할 것.
