## 1. 🔴 지금 당장 해야 할 일 — DB 마이그레이션 수동 적용

**이번 세션에서 제가 직접 DB에 적용하지 못한 마이그레이션이 있습니다.** 지금 로컬에 있는 서비스 롤 키(`SUPABASE_SERVICE_ROLE_KEY`)는 REST 레벨 접근만 가능하고, `ALTER TABLE` 같은 DDL을 실행할 방법(Management API 토큰, 직접 Postgres 연결 문자열, `exec_sql` 같은 RPC 헬퍼)이 `.env.local`에도 DB에도 없습니다. **다음 담당자가 Supabase 대시보드의 SQL 에디터에서 아래 파일 내용을 직접 실행해야 합니다**:

```
supabase/migrations/040_review_started_at.sql
```

내용은 `project_matches` 테이블에 `review_started_at TIMESTAMPTZ` 컬럼 하나 추가하는 것뿐입니다. **이걸 적용하기 전까지는**:
- 리뷰어가 리뷰를 시작해도 시작 시각이 기록되지 않습니다(에러는 안 나고 조용히 무시됨 — `app/api/reviews/[matchId]/start/route.ts`가 컬럼이 없어도 500을 안 던지도록 짜여있진 않아서 실제로는 **API가 500 에러를 반환할 수 있습니다** — 아래 참고).
- 리포트의 "평균 응답 소요시간" 섹션이 계속 안 보입니다(데이터가 없으면 조용히 숨겨지도록 처리해뒀습니다).

**⚠️ 추가 확인 필요**: `app/api/reviews/[matchId]/start/route.ts`는 `project_matches.review_started_at`을 select/update하는데, 마이그레이션 미적용 상태에서 이 컬럼이 실제 DB에 없으면 Supabase가 에러를 반환합니다. `ProjectCardExpandable.tsx`에서 이 API를 `.catch(() => {})`로 감싸서 호출하므로 리뷰 진행 자체는 안 막히지만, 마이그레이션 적용 전까지 이 API는 실질적으로 계속 실패만 하고 있을 겁니다. **마이그레이션 적용 후 실제로 한 번 리뷰를 끝까지 제출해보면서 정상 동작하는지 확인 권장.**

## 2. 관리자/리뷰어 진행중 카운트 불일치 수정

**증상**: 관리자 패널 "진행 중 프로젝트"는 1개인데 리뷰어 화면엔 2개로 나옴.

**원인**: 관리자 통계([app/admin/page.tsx:20](app/admin/page.tsx#L20))는 `projects.status === 'active'`만 세고 있었는데, 리뷰어 대시보드는 `project_matches.status === 'accepted'`(리뷰어가 참여 중인 매칭)를 셉니다. 7/27에 추가된 모집마감 3단계 시나리오 기능 때문에 프로젝트가 `active → reviewing`으로 넘어갈 수 있게 됐는데, 관리자 통계가 `active`만 세도록 안 고쳐져 있어서 숫자가 갈렸습니다.

**수정**: `.eq('status', 'active')` → `.in('status', ['active', 'reviewing'])`로 변경 — "끝나지 않은 프로젝트"라는 동일한 기준으로 통일.

*(이 두 항목은 이미 커밋 `e9e226a`로 GitHub에 푸시된 상태입니다 — 이 문서엔 맥락 유지를 위해 요약만 남깁니다.)*

## 4. 인사이트 모달 + 라운지 소셜 기능 버그 수정

### 4-1. 인사이트 모달
- **다음/이전 글 버튼을 누르면 모달이 꺼지던 버그**: `InsightModalNav`의 버튼들이 배경 오버레이(클릭 시 닫힘) 안에 형제로 떠 있어서, 버튼 클릭 이벤트가 오버레이까지 버블링돼 `onNext`/`onPrev`가 실행된 직후 오버레이의 "배경 클릭 시 닫기" 핸들러도 같이 실행되고 있었음 — `stopPropagation` 추가로 수정 ([components/shared/InsightModalNav.tsx](components/shared/InsightModalNav.tsx)).
- **스크롤 영역이 카드 밖으로 못생기게 튀어나오던 문제**: 스크롤 컨테이너에 카드와 동일한 `rounded-[28px]`가 안 씌워져 있었음 — [components/shared/SharedFeedPanel.tsx](components/shared/SharedFeedPanel.tsx), [components/shared/SharedScrapGrid.tsx](components/shared/SharedScrapGrid.tsx) 둘 다 수정.
- **댓글이 새로고침하면 사라지는 것처럼 보이던 문제**: DB 직접 조회로 실제 저장은 정상 확인됨(버그 아님) — 다만 새로고침 후 댓글 패널이 항상 접힌 채로 시작하고 개수 표시가 전혀 없어서 "사라졌다"고 오해하기 쉬웠음. [components/shared/InsightDetailView.tsx](components/shared/InsightDetailView.tsx)에서 상세 조회 API가 이미 내려주던 `comment_count`를 버튼에 항상 표시하도록 수정.
- 스크랩 저장 위치는 버그 아님 — "스크랩한 글" 링크가 인사이트 목록 상단에 이미 있음(발견하기 어려웠던 것).

### 4-2. 라운지 — 좋아요만 되고 나머지는 장식이던 것 실제 구현
확인 결과 `Repeat2`(리포스트)/`Share2`(공유)/`MessageSquare`(댓글) 아이콘이 라운지 글 카드에서 **`onClick` 자체가 연결 안 된 순수 장식**이었습니다(좋아요만 실동작). "내가 쓴 글" 목록도 삭제 기능이 없었습니다. 전부 새로 구현:
- **댓글**: 기존 API(`/api/lounge/posts/[id]/comments`, GET/POST 이미 존재)에 UI 연결 — 카드 안에서 스레드 펼치기/작성 가능.
- **공유**: 글 내용 + 현재 페이지 링크를 클립보드로 복사(라운지엔 글 단위 개별 페이지가 없어서 페이지 링크로 대체 — 아래 §8 참고).
- **리포스트**: 새 테이블 없이, 원글을 인용문으로 미리 채운 컴포저를 열어서 **실제로 새 `lounge_posts` row로 저장**하는 "인용 리포스트" 방식으로 구현.
- **"내가 쓴 글" 삭제**: 신규 `DELETE /api/lounge/posts/[id]/route.ts`(RLS `lounge_posts_delete: auth.uid() = author_id`로 본인 글만 가능, 서버에서도 이중 확인) + 사이드바에 삭제 버튼 추가.

## 5. 리포트 콘텐츠 고도화 (이번 세션의 핵심 작업)

사업주가 직접 "확인사항 1"(파이프라인 사실관계 7개 질문)과 "확인사항 2"(콘텐츠 확장 스펙, 우선순위 1~3)를 순서대로 요청해서 진행했습니다.

### 5-1. 확인사항 1 — DB 직접 조회로 확인한 사실
- **`domain_tags`(직군)**: 가입 폼엔 없고 `/evaluator/settings`에서만 선택적 입력. **실측: 리뷰어 5명 중 0명 채움.**
- **모델**: `lib/ai/generateReport.ts`가 `callClaude(prompt, 'sonnet', ...)`로 **Claude Sonnet** 사용 확정(`lib/ai/gemini.ts`는 어디서도 import 안 되는 죽은 코드). 입력 데이터 절단 로직 없음 — 전원 전체 답변을 그대로 프롬프트에 넣음.
- **`ai_reports`**: `project_id UNIQUE` + `upsert` 그대로 — 재생성하면 이전 리포트 완전히 사라짐(§6 Phase 3에서 다룰 예정, 미착수).
- **`is_unlocked: true`** 하드코딩 유지 중. 티어는 등록 시점 고정, 변경 UI 없음.
- **`question_summary` 포함 기준**: `question_type`이 `multiple_choice`/`likert_5`/`likert`/`sean_ellis`만 — 서술형(`short_answer`) 완전 배제.
- **품질 스크리닝**: DB 트리거는 없음. `quality_score` 컬럼은 죽은 컬럼(계산/조회 코드 전무). *(단, 이후 재확인에서 클라이언트 폼 레벨의 단답 차단 로직을 발견 — §6 참고. 이건 이전 확인 때 놓쳤던 부분으로, 사업주에게 정정 답변드림.)*
- **소요시간/글자수 메타데이터**: `review_answers`엔 저장 안 됨.

### 5-2. 확인사항 2 — 콘텐츠 확장 (우선순위 1·2 완료, 3 보류)

**우선순위 1 — Claude 프롬프트/응답 스키마 확장** ([lib/ai/prompt.ts](lib/ai/prompt.ts), [lib/ai/generateReport.ts](lib/ai/generateReport.ts)): 같은 호출(새 API 호출 아님)에 4개 필드 추가 요청.
- `reviewer_narratives`: 리뷰어별 2~3문장 요약 + 원문 인용 1개(최대 5명)
- `strongest_objection`: 가장 강한 반대/우려 의견 원문 1개(없으면 null)
- `theme_frequency`: 서술형에서 반복되는 주제 최대 5개 + 언급 인원수 + 원문 샘플
- `verbatim_quotes`: 위 항목과 안 겹치는 원문 인용 3~5개 + 질문 맥락

리뷰어를 일관되게 "리뷰어 A"/"리뷰어 B"로 지칭하도록, Claude가 즉석에서 라벨을 지어내지 않고 우리가 `reviewerTag(index)`로 미리 태그를 붙여서 프롬프트에 넘깁니다. 응답 필드 증가로 `max_tokens`를 8000→12000으로 상향.

**우선순위 2 — 표시 레이어(AI 호출 없음, 코드 계산)**:
- `question_summary`에 "N명 중 M명" 분수 표기 추가.
- `panel_summary`: 직군/성별/연령대별 인원수를 코드로 집계 — **단, `domain_tags`가 실질적으로 0%라 직군 쪽은 지금 당장은 "미입력"만 나올 가능성이 높습니다.**

**화면 반영**: [components/report/StandardReportView.tsx](components/report/StandardReportView.tsx)에 위 필드들 + 패널 프로필 카드를 새 섹션으로 추가, [app/builder/reports/[id]/page.tsx](app/builder/reports/[id]/page.tsx) 타입/props 전체 배선 완료.

**우선순위 3(문항×인구통계 교차분석)은 명시적으로 보류 지시 — 미착수.**

### 5-3. 그 외 UI 버그 수정
- **상단 "AI 리포트 · 재생성" 바가 리포트 카드에 겹쳐 보이던 버그**: `sticky top-20`이 `CreatorLayout`의 (고정 아닌) 일반 흐름 헤더를 기준으로 잘못 계산돼 있었음 → `sticky top-0` + 불투명 배경 + 경계선/그림자로 수정.
- **리커트(1~5점) 문항 응답이 "3", "5" 숫자로만 노출되던 버그**: 답변 저장 자체가 숫자 문자열이라(라벨 텍스트 없음), 집계 로직에 `LIKERT_LABELS`를 추가해 "3 · 보통이다"처럼 라벨을 붙임. "재생성" 누르면 기존 리포트도 바로 반영(집계를 매번 원본에서 새로 계산하는 구조).

## 6. 🔴 리뷰어 품질 관리 재검토 — Phase 1 완료, 2~6 미착수

사업주가 별도 설계 문서(`FindFit_베타_리뷰어퀄리티_강제화_설계.md` — **이 파일은 리포지토리 밖 사업주 개인 문서함에만 있고, 리포지토리 안에는 없습니다.** 필요하면 사업주에게 직접 요청할 것)를 기준으로 6단계 작업을 요청했고, 진행 중 아래 사실들을 코드/DB 직접 확인으로 정리했습니다.

### 6-1. 재확인 과정에서 발견한 것 (정정 사항)
이전에 "품질 스크리닝 트리거가 코드/DB 어디에도 없다"고 답했던 것에 **중요한 누락이 있었습니다**: DB 트리거는 확실히 없지만, **클라이언트 폼(리뷰 제출 화면)에는 실제로 단답 차단 로직이 존재합니다**:
- [components/evaluator/ProjectCardExpandable.tsx:71-72](components/evaluator/ProjectCardExpandable.tsx#L71): `MIN_SHORT_ANSWER_LENGTH = 5`, `CARELESS_ANSWER_PATTERN = /^[.,!?~…\s]*$/`
- 모든 `short_answer` 타입 문항(PSF-2 포함)에서 답변이 5자 미만이거나 마침표/물음표/공백뿐이면 제출 자체가 막힘.
- **단, 서버(`app/api/reviews/[matchId]/submit/route.ts`)엔 이 검증이 전혀 없습니다** — 화면을 거치지 않고 API를 직접 호출하면 우회 가능한 구조입니다.

### 6-2. 리뷰어 인구통계 데이터 채움 현황 (DB 직접 조회)
| 필드 | 채움 비율 | 입력 시점 |
|---|---|---|
| `birth_date`(생년월일) | **5명 중 5명 (100%)** | 회원가입 폼, 만 19세 게이트로 사실상 필수 |
| `gender`(성별) | **5명 중 2명 (40%)** | 회원가입 폼에 있지만 **선택 항목**으로 명시 |
| `domain_tags`(직군) | **5명 중 0명 (0%)** | `/evaluator/settings`에서만, 완전 선택 |

### 6-3. 고정 문항 필수 여부
`PSF_STANDARD_QUESTIONS`(psf-1~4) + `SEAN_ELLIS_QUESTION` 전부 **필수**입니다. `Question` 타입에 `is_required`/선택 개념 자체가 없고, 제출 검증 로직이 "질문 목록 전원 답변 필수"로 짜여 있어 고정 문항이든 크리에이터 커스텀 문항이든 전부 필수입니다. 즉 **PSF-2(서술형)는 항상 답변이 있다는 뜻**이라, §5의 리포트 서술형 의존 섹션(리뷰어별 의견/우려 의견/반복 주제/원문 인용)이 생각보다 자주 채워질 가능성이 높습니다.

### 6-5. Phase 2~6 — 미착수, 다음 담당자가 이어서 할 것
사업주가 원래 요청한 순서대로, **각 Phase 완료마다 보고하고 다음으로 넘어가는 방식**으로 진행 중이었습니다. Phase 1만 끝난 상태에서 "지금까지 푸시 + 인수인계서 작성" 요청이 들어와 여기서 멈췄습니다.

- **Phase 2 — 직군(domain_tags) 필수 입력화**: 매칭 수락 시점에 `domain_tags`가 비어있으면 관심 카테고리 선택을 강제하는 게이트 추가. 기존 가입자도 다음 매칭 수락 때 동일 적용. **미착수.**
- **Phase 3 — 리포트 버전 히스토리 보존**: `ai_reports` upsert 직전에 기존 행을 `ai_reports_history`(신규 테이블, project_id/이전 report_data/생성시각만)로 복사. UI는 불필요, 데이터 보존만. **미착수.**
- **Phase 4 — 카테고리 벤치마크 코멘트 정직화**: 지금 `benchmark_comment`가 AI가 실제 비교 수치 없이 지어내는 구조인지 먼저 코드로 확인 필요(`report_benchmark_logs` 테이블이 이미 있고 `computeConfidenceTiers`가 존재하니 이 근처를 볼 것 — `lib/ai/generateReport.ts:164-174`, `lib/ai/confidenceTiers.ts`). 확인 후 3건 이상이면 실제 평균과 비교, 미만이면 "비교 데이터 부족" 정직 표시로 교체. **미착수(확인조차 안 됨).**
- **Phase 5 — Light 리포트 `verbatim_quotes` 추가**: 기존 Light 프롬프트 스키마(`lib/ai/prompt.ts`의 `buildLightPrompt`)에 원문 인용 2~3개 필드만 추가, `LightReportView.tsx`에 반영. **미착수, 다만 범위가 작아 난이도 낮음.**
- **Phase 6 — Van Westendorp 가격 민감도 문항**: 사업주가 명시적으로 "착수 전 스펙/공수 추정만 먼저 보고"하라고 지시함. **분석도 시작 안 함.**
